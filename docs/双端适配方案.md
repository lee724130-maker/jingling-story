# 精灵物语 · 双端适配方案（决策文档）

- 版本：v1.0
- 日期：2026-11-17
- 决策项：规划文档 11.4-A「React Web → 微信小游戏」技术路线
- 状态：**已定案**，待阶段 0 资质就绪后进入 POC 验证

---

## 0. 结论先行（TL;DR）

> **推荐路线：Cocos Creator 3.x 重做「表现层」，后端 + shared 规则层 100% 复用，双端共享同一存档。**
>
> 同时**否决**规划文档里写的「Taro/Remax 适配层」——那是一条走不通的路（见第 1 节）。

三条路线对比与结论：

| 路线 | 结论 | 一句话理由 |
|---|---|---|
| Taro/Remax 适配层 | ❌ 否决 | 概念性错误：Taro 面向「小程序」，本项目要上的是「小游戏」，两者运行环境中一个本质区别是**小游戏没有 DOM** |
| Three.js 硬移植小游戏（`threejs-miniprogram`） | ⚠️ 不推荐 | 官方适配库停在 Three.js **0.108**（2021 年最后更新），本项目用 0.169，且 R3F/Drei 深度依赖 DOM 与 React 渲染器，改造成本≈重写 |
| **Cocos Creator 3.x 重做表现层** | ✅ **推荐** | 微信官方一级引擎插件支持、原生支持 3D、一键导出小游戏、Web 端也能出，长期维护，是 3D 小游戏的主流选择 |

**核心策略**：不追求「一份代码两端跑」，而是「**一份逻辑两端跑**」——把游戏拆成 3 层，只有表现层需要各写一套。

## 1. 必须先纠正的认知：微信小程序 ≠ 微信小游戏

这是本次决策最重要的前提，规划文档 11.4-A 把它混淆了。

| 维度 | 微信小程序（Mini Program） | 微信小游戏（Mini Game） |
|---|---|---|
| 运行环境 | 有类 DOM 环境，页面式 | **无 DOM / 无 BOM，无全局 document / window** |
| UI 方式 | WXML + WXSS 组件树 | 整屏一块 Canvas，所有按钮/文字都是「画」出来的 |
| 渲染循环 | 事件驱动 | 逐帧 `requestAnimationFrame` 游戏循环 |
| 代表框架 | **Taro / Remax / uni-app** | **Cocos Creator / LayaAir / 白鹭** |
| 本项目对应关系 | ❌ 不适用 | ✅ 本项目要上架的是这个 |

**关键证据**：微信官方文档明确「小游戏的运行环境在 iOS 上是 JavaScriptCore、Android 上是 V8，**都没有 BOM 和 DOM**，没有全局 document 和 window 对象；用 DOM API 创建 Canvas/Image 会报错」。微信官方「游戏引擎插件」页列出的一级支持引擎是 CocosCreator / CocosCreatorV3 / LayaAir 1.x/2.x/3.x / 白鹭——**没有 Taro、没有 React、没有 Three.js**。

**结论**：Taro/Remax 从根上就不适用于小游戏。这个选项应当从规划文档中永久移除。

## 2. 当前架构盘点：哪些能复用，哪些要重写

采用三层拆分：

```
┌─────────────────────────────────────────────┐
│  L3 平台适配层（薄）                          │
│  Web: localStorage / fetch                  │
│  小游戏: wx.login / wx.setStorage / wx.request│  ← 每端各写一份，很薄
├─────────────────────────────────────────────┤
│  L2 表现层（厚）                              │
│  Web: React + R3F + Canvas 特效层             │
│  小游戏: Cocos Creator 场景 + TS 组件          │  ← 唯一需要重写的部分
├─────────────────────────────────────────────┤
│  L1 逻辑与数据层（厚，100% 复用）              │
│  server/  NestJS + MySQL 权威结算/存档/登录    │
│  shared/  types.ts / gamedata.ts / rules.ts   │  ← 两端共用，零改动
└─────────────────────────────────────────────┘
```

| 层 | 资产 | 是否复用 | 说明 |
|---|---|---|---|
| L1 后端 | `server/` NestJS + MySQL `jingling_story` | ✅ 100% | API、JWT、权威结算、存档乐观锁原样使用，小游戏只是多一个客户端 |
| L1 共享 | `shared/rules.ts`（伤害/捕获/升级/进化/checksum） | ✅ 100% | 纯 TS 函数，无 DOM 依赖，Cocos 项目可直接引用；**这是保证双端数值一致的关键** |
| L1 共享 | `shared/gamedata.ts` / `types.ts` | ✅ 100% | 配置与类型，Cocos TS 直接 import |
| L2 美术 | `web/public/art/*.png`（训练师/精灵/场景） | ✅ 素材复用 | PNG 是通用资源，导入 Cocos 即可，重做的是「怎么渲染」不是「画什么」 |
| L2 引擎 | `Scene3D.tsx` / `engine.ts` 状态机 / `battleFx.ts` | ⚠️ 逻辑复用、代码重写 | 状态机设计可照搬，Three.js 绘制代码不能直接用 |
| L2 UI | `components/*.tsx`（战斗/图鉴/菜单） | ❌ 重写 | React 组件 → Cocos 节点 + TS 脚本 |
| L3 平台 | `api/client.ts` | 🔶 薄改 | fetch → `wx.request`；登录 → `wx.login` + code 换 openid |

**好消息**：项目从一开始就把规则抽到了 `shared/`，且后端做了权威结算——这正是双端共享最难的部分，已经做对了。真正要重写的只是「表现层」，而表现层是纯前端工程，不碰数据与数值正确性。

## 3. 平台硬约束（官方文档数据，决策依据）

| 约束 | 官方数值 / 事实 | 来源 |
|---|---|---|
| 代码包总大小 | ≤ **30M** | 微信开放文档《代码包》，2026-04-09 更新 |
| 主包大小 | ≤ **4M** | 同上 |
| 单个分包 | 不限制大小 | 同上 |
| DOM / BOM | 无全局 document / window | 微信开放文档《小游戏和小程序区别》 |
| 渲染能力 | 支持大部分 Canvas 2D 与 WebGL **1.0**（RenderingContext） | 微信开放文档《使用游戏引擎》 |
| 引擎插件 | CocosCreator(V3) / LayaAir 1-3.x / 白鹭；引擎作为插件在微信客户端缓存，提升启动速度 | 微信开放文档《游戏引擎插件》，2026-07-05 更新 |
| `threejs-miniprogram` | Three.js **0.108.0**，最后实质更新 2021-04，Controls 未适配 | github.com/wechat-miniprogram/threejs-miniprogram |

**对方案的直接影响**：
- 必须做**分包 + 远程资源加载**：主包只放启动代码，美术素材（训练师/精灵/场景 PNG、后续音效）放分包或 CDN。当前 AI 素材是 PNG，体积可控，但要在 Cocos 里做资源分包规划。
- WebGL 只保证 **1.0**，Cocos 3.x 会处理兼容，比自己用 Three.js 裸写稳。
- 引擎插件能显著减小代码包（引擎不占自己的 4M 主包），Cocos 3.x 有官方插件，这是选它的重要现实理由。

## 4. 为什么 Three.js 路线被否决（详细）

有老板可能会问：既然 Web 端 Three.js 已经跑通了，为什么不直接移植？三个硬伤：

1. **适配库版本太旧**：`threejs-miniprogram` 官方停在 Three.js 0.108（2021 年），本项目用 0.169，跨了 60 多个版本。要升级就得 fork 适配层自己改，等于维护一个私有引擎分支。
2. **R3F/Drei 无法移植**：React Three Fiber 是 React 渲染器，Drei 的 `useTexture`/控制器都依赖 DOM、React 调和机制和浏览器 API。小游戏无 DOM，这套东西不是「适配」能解决的，是「推倒」。
3. **无引擎插件加速**：Three.js 不在微信引擎插件列表，全部代码要塞进自己的 4M 主包；Cocos 可用官方插件把引擎外置。

**成本对比**：硬移植 Three.js ≈ 重写渲染层 + 维护私有适配库 + 自己解决分包/资源/输入；直接用 Cocos ≈ 重写渲染层 + 官方工具链解决其余一切。后者明显更划算。

## 5. 推荐方案落地：Cocos Creator 3.x

### 5.1 目录规划（新增 `minigame/` 兄弟目录，不动 `web/`）

```
精灵物语/
├── web/            # 现有 React Web 版，继续独立迭代（不删不改）
├── server/         # NestJS 后端，100% 复用
├── shared/         # 规则/配置/类型，100% 复用 ← Cocos 项目直接引用
├── minigame/       # 新增：Cocos Creator 3.x 工程
│   ├── assets/
│   │   ├── scripts/      # TS 游戏逻辑（复用 shared 规则）
│   │   ├── art/          # 从 web/public/art 复用/转换的素材
│   │   └── scenes/       # 世界地图 / 战斗 / 图鉴等场景
│   ├── settings/         # 小游戏构建配置（分包、插件）
│   └── build-wechatgame/ # 构建产物（微信开发者工具打开）
└── docs/
```

**关键决策**：Web 版保留，不合并、不废弃。两端并行迭代，共享 L1。这样 Web 端已完成的成果不浪费，且 Web 版本身就是一个可上架的平台。

### 5.2 三步走迁移路径

**第 1 步：POC 最小验证（资质就绪前就能做，用测试号）**
- 装 Cocos Creator 3.x，建 `minigame/` 工程
- 导入现有 AI 素材（训练师 + 1 只精灵 + 草原场景）
- 复刻最小闭环：虚拟摇杆控制角色 → 走近野怪触发 → 投球 → 出精灵 → 放一次带特效的技能
- 接入后端：用临时测试号验证 `wx.login` → code 换 openid → `GET /api/player/save` 拉存档（或先用现有本地测试账号跑通 API）
- 用微信开发者工具构建预览，实测：①3D 能渲染 ②API 能联通 ③主包 <4M
- **POC 通过才进入第 2 步**（这是防止返工的闸门）

**第 2 步：核心玩法对齐（POC 通过后）**
- 把 `engine.ts` 的状态机逻辑用 TS 在 Cocos 里重写：地图/野怪游荡/投球过场/回合战斗/捕获/养成
- 战斗规则直接 import `shared/rules.ts`，保证与 Web 端数值完全一致
- 技能特效：Cocos 的粒子系统重做 8 属性特效（复用 `battleFx.ts` 的设计思路）
- 结算走服务端 `settleBattle/settleCapture`，与 Web 端同一套防作弊

**第 3 步：双端互通与上架**
- 登录接微信 UnionID（依赖阶段 0 资质），同一 uid 拉同一存档
- 验证跨端：Web 改存档 → 小游戏刷新看到相同结果
- 分包优化、包体瘦身、提审上架

### 5.3 需要老板配合/决策的点

| 事项 | 说明 |
|---|---|
| 装 Cocos Creator 3.x | 需老板在本机安装（约 2-4GB），或用已有安装 |
| 微信开发者工具 + 测试号 | POC 阶段用测试号即可，不依赖营业执照 |
| 资质（阶段 0） | 只在「第 3 步真机登录 + 上架」时卡住，不阻塞 POC 和第 2 步 |

## 6. 风险与回退策略

| 风险 | 概率 | 应对 |
|---|---|---|
| Cocos 3D 在小游戏低端机性能不足 | 中 | POC 阶段就用低端机/开发者工具性能面板测；必要时降级为 2.5D 广告牌（与 Web 版思路一致） |
| 包体超 4M 主包 | 中 | 素材分包 + 远程加载；Cocos 引擎走官方插件外置 |
| 双端表现不一致引发体验割裂 | 中 | 规则层共用 `shared/`，表现层允许差异；明确「数值一致、画面各有特色」的定位 |
| 资质迟迟下不来 | 高 | POC 与核心玩法不依赖资质，可先做完；只把真机登录和上架留到资质就绪 |
| Cocos 学习成本（老板熟 React 不熟 Cocos） | 中 | 若团队抗拒，备选 LayaAir 3.x（也是官方插件、也支持 3D、TS 语法更接近前端）；决策方法不变，只是换表现层工具 |

**最终回退底线**：即使小游戏端整体推迟，Web 端 + 后端 + 权威结算已是完整可玩产品，不构成沉没成本。
